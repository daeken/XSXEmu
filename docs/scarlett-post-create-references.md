# Scarlett post-create device calls: reference comparison

Static caller facts are from the pinned image in the [ABI map](xbox-d3d12-abi.md); addresses are RVAs. VIctory `940d32f69b22265690a0b5a15d6ded572ba33baf`, XCL `91f9a5e9f03156ea82dc55a18f7704862da7a5db`, and the local Leonida reports (boot experiment reports base `1cc6e3c12` plus local changes) were inspected read-only for facts. These are compatibility implementations, not native Xbox observations. The Leonida XMem census names the same title hash; neither that fact nor other title/build similarities establish identical native runtimes.

## Optional #49, then a distinct title allocation

- At `02478628` a prior byte flag gates the branch; `02478677`–`0247867a` additionally checks a packed, version-like value against `0x000a000065f4259c`. The optional dispatch at `02478698` loads device `08759d00` into `RCX`, sets `EDX=0x11f`, `R8D=1`, and calls vtable `+0x188` (#49). No `R9` or stack argument is prepared at that callsite, and no return is consumed. The title writes its own byte `0765a6d9=1` **before** calling #49. The flag and comparison do not prove whether the live branch is taken, what #49 does, or whether effects can be omitted. Desktop #49 in the pinned DirectX-Headers is `OpenExistingHeapFromFileMapping`; its handle/IID/output contract is unrelated. VIctory's `device.rs` table leaves #49 on its missing-method logger (`object.rs`, returns `E_NOTIMPL`); XCL's `real.rs` `console_slots` has no Xbox #49 override in the desktop-backed path. Leonida `retail_boot_chain.md` does not report #49 behavior. None validates its omission.
- The joined path at `024786b9` calls `XMemVirtualAlloc(NULL, 0x10000, 0x20401000, 0x283, 0x42404)`. It checks the full pointer (null breaks), then calls `VCRUNTIME140!memset` at `024786dc` with fill zero and length `0x10000` (thunk `05f40580`, IAT `06794368`). The caller stores the returned **allocation** address (saved in `RSI`, not the memset return) in globals `075e7020` and `075e7028`. At `05886610`–`05886657` an aligned bump allocation uses the latter as the atomic cursor and bounds the new cursor against the former plus `0x10000`. Cleanup at `0248bded`–`0248be20` tests the base, passes that address, `0x10000`, and `0x8000` to the title's `VirtualFree` IAT (`06793a70`), then zeroes both globals. This establishes a separate title-managed 64 KiB arena, not that it lacks graphics uses. It is not evidence for reserving or satisfying the device's likely 1 MiB graphics ring.
- Leonida `xmem_exe_calls.md` records the exact allocation metadata tuple once, and describes a baseline shim refusing its nonzero attributes; that census is not a successful allocation trace. VIctory `crates/victory-hle/src/modules/xmem.rs::XMemVirtualAlloc` and XCL `crates/xcl/src/hle/kernelx.rs::XMemVirtualAlloc` adapt allocation/protection metadata in different host models. No matching native allocation result or complete cache/GPU policy is established by those adapters. The [XMem ABI notes](xmem-boot-abi.md) track that tuple separately.

## Exact IID correspondence and first diagnostic gate

The full requested device IID `5405c344-d457-444e-b4dd-2366e45aee39` matches VIctory's `device.rs` trigger for its newer queue/list layout. It still uses the **same HLE device slots** for #8/#26 and leaves #49 missing. The trigger is a process-wide heuristic, not a per-object native IID map. For the same title RVA `024841a6`, VIctory `queue.rs` explicitly maps queue #18 to a frequency query in that variant; its 100 MHz value is synthetic. XCL `real.rs::queue_dispatch` instead identifies queue revisions from known fence arguments at #14/#15 versus #16/#17, or calls to identified newer device methods. On an undetermined revision XCL's #18 fallback copies eight bytes of a desktop description; that is **not** a frequency oracle. Leonida's Windows proxy run reports the device #26/#8 sequence; it does not provide a native Xbox per-IID table or calibrated queue value. The direct-queue caller itself is stronger evidence for #18 transport than any of these heuristics.

After separately admitted experimental device creation, the fastest defensible gate is a terminal post-create trace on the exact observed device, not enabling #8 in isolation. Record which non-prefix slot is reached first: if #49, stop before effects and record its scalars; otherwise first #26 should show the receiver in `RDX` and the `(1,1)` selector pair. Log the output address without reading or writing the pointed-to bytes. An owned test can assert the chosen slot and register transport without guest execution. Only after the intervening title arena and slot-26 policy are explicitly handled should a slot-8 trace be used to compare the exact tuple, queue IID and output address with the owned fixture. Stop before publication if queue semantics remain unsupported. Neither observed argument order nor an ignored return justifies reporting success.

None of these references resolves device creation flag `0x20` or when/how the graphics ring is created. The 64 KiB arena evidence narrows the next owned memory-lifetime fixture but does not authorize a native device success, a synthetic #49 success, or a #26 write. Prefer matching GXDK declarations/documentation or controlled native execution of an original sample for effects, and keep title execution out of this comparison.
