# Scarlett device creation: evidence and remaining invariants

The terminal caller probe identified one profile of the pinned executable in [the ABI map](xbox-d3d12-abi.md), not a successful creation. Only the caller-written 80-byte extent and 16-byte IID were read. The output pointee was not accessed. The [owned fixture](xbox-device-owned.md) supplies 80 instances of `0x5a` (every byte differs) and proves host lifetime and actual Metal completion, not retail settings. No raw capture is included.

## Nonzero words

The independently inspected [Microsoft Xbox sample, pinned `b1e77b6`](https://github.com/microsoft/Xbox-GDK-Samples/blob/b1e77b6ac10f95b07296025fda171ca2ddc42dbe/Samples/IntroGraphics/SimpleDeviceAndSwapChain/SimpleDeviceAndSwapChain.cpp#L251-L305) demonstrates named fields and sample policy. [Ebitengine's x64 `HostLayout` binding, pinned `d438df6`](https://github.com/hajimehoshi/ebiten/blob/d438df689b19544c82543ad522b36be86a5a60b7/internal/graphicsdriver/directx/d3d12_windows.go#L816-L835) independently puts those fields at the matching offsets. These corroborate the field roles, not the exact revision's validation, timing, or complete struct layout.

| Offset and observed LE value | Corroborated role | Creation invariant vs first later use |
| --- | --- | --- |
| `+00 = 0x20004` | `Version`; Microsoft sample passes `D3D12_SDK_VERSION`. VIctory reports the same word on different device/interface layouts. | Pin the observed version **and** IID/build; do not select a vtable by version alone. Exact native acceptance rules are unknown. No later method can repair a wrong ABI choice. |
| `+08 = 0x100000` | `GraphicsCommandQueueRingSizeBytes`; likely a 1 MiB requested graphics ring under the corroborated layout. The sample passes a default-size constant, not evidence that this literal is a default. | Must preserve the requested graphics queue policy at creation. Whether backing/reservation is required before successful return, or can be materialized at graphics queue creation/submission, is not established. An internal Metal queue or byte allocation of the same size is not an Xbox ring. |
| `+20 = 1` | `DisableGeometryShaderAllocations`; sample says setting it saves title memory if GS is unused. | Suppress any modeled GS backing at creation and carry the restriction into relevant pipeline validation. Native allocation timing/size and behavior on later GS use are unknown; no evidence that title uses a GS on this device. |
| `+24 = 1` | `DisableTessellationShaderAllocations`; sample says setting it saves title memory if DS/HS are unused. | Same negative allocation policy for tessellation; enforce scope at relevant pipeline creation/use. No proof of native allocation timing, size or feature-query/error behavior. |
| `+28 = 1` | `DisableDXR`; sample says setting it saves title memory if DXR is unused. | Do not allocate or advertise working DXR on this profile. Later DXR operations need their own contract; whether the native disable flag requires any work beyond not allocating DXR, and the exact later errors, are unknown. |
| `+3c = 0x20` | `CreateDeviceFlags`; sample uses `..._NONE`, not this bit. | **Unresolved creation blocker.** Neither the bit definition nor its phase/effect was found. Cannot classify it as deferred, ignorable, debug, or a resource flag. |

The zero words are not proven *required* defaults. In the comparator layout, `+04` is debug flags (sample leaves it zero when neither DEBUG nor PROFILE is defined), `+0c` would be x64 alignment padding, `+10..17` is an off-chip tessellation buffer address, `+18/+1c` are scratch sizes (Microsoft explicitly leaves them zero for its no-scratch shader sample, not a universal rule), `+2c` is a DPBB opt-out, `+30..37` and `+38` are the DXR stack address and size override, `+40` is AutoHDR paper white, and `+44` is a command-segment chaining opt-out. Observed zero addresses do not prove when the driver supplies backing; observed false opt-outs do not demonstrate host-equivalent DPBB or command chaining. `+48..4f` are not covered by the comparator; the sample names amplification buffer settings without offsets, so do not interpret that tail as reserved or assign fields to it. Keep exact zeros in a diagnostic matcher, not in a guessed public native ABI. Do not read beyond `+4f`.

## Read-only reference cross-checks and missing evidence

* XCL `91f9a5e`: logs the first word as SDK version, but the host path receives only IID/output and the null path ignores params. This is not an independent test of sizes, disables, flags, or zero defaults.
* Leonida, local `docs/d3d12_xs_surface.md` §7.1 and `docs/d3d12_vulkan.md`: points to the sources above and describes logging/forwarding, not controlled parameter mutations. Its 24-word logs do not extend this caller's readable contract.
* VIctory `940d32f`: device creation reads only the first parameter word, warns on version mismatch, and uses IID as a layout cue in its own approximation. Its later graphics behavior is not evidence of native treatment of the other fields. No implementation was copied from any reference.

Request the lawfully accessible **Xbox Series GXDK edition matching the observed call**: the `D3D12XBOX_CREATE_DEVICE_PARAMETERS` declaration (field offsets/types/size), `D3D12_SDK_VERSION`, `D3D12XBOX_CREATE_DEVICE_FLAGS` with `0x20` identified, and its creation/queue memory-policy documentation. A header can resolve layout and enumerants but cannot by itself settle timing. If documentation does not specify timing/defaults, the necessary behavioral evidence is a controlled **original sample on the corresponding native GDK runtime** (no title): hold IID/build fixed, vary just `0x20`, ring request, each disable, and candidate zero field; record HRESULT and memory/feature delta immediately before/after creation, then at direct-queue creation/first submission or relevant pipeline operation. Start with `0x20` vs none and default vs requested ring. An HLE that ignores the field cannot supply that evidence.

## Concrete owned-only follow-up

Split *profile recognition* from *creation authorization*. A bounded pure classifier can distinguish the exact pinned opaque request, an independent synthetic profile, and mismatch. The retail match returns **recognized, unsupported creation effects**, never a backend permit. Give only the synthetic plan a private permit; unit-test one-byte mutations throughout the extent, wrong adapter/IID, and recognition with no factory side effects. Keep guest spans and launch policy outside the host stage.

Extract the production-shaped Metal ownership core from test support: stage an owned device and command queue in a host-only Rust module, reuse the bounded identity ledger, and retain explicit host-only teardown. Use deterministic failures for device open, queue open, ledger admission, and final output publication. Verify no live entry or leaked refs on failure, one canonical identity on successful owned publication, exact final release, and the existing real same-queue readback/retirement. Keep Mach access, test counters, the guest vtable, and the fixed-copy fixture outside the owner. This gives an independently tested lifetime transaction without any title import/provider or claim that Metal realizes the ring or flag.

The subsequent optional #49, separate 64 KiB XMem call, hidden-output-first #26, and #8 queue contract are distinct gates. They were not executed in the capture. Ring materialization may affect the later queue contract, but the existence of that method does not prove creation may ignore the request. Do not run the title to discover behavior behind fabricated success.
