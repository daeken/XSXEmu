# Native vertex MODE and scalar launch audit

Read-only follow-up to the [graphics binding cohorts](graphics-binding-cohorts.md#exact-e32-unsigned-conversion-from-s10). On the pinned expanded library and LLVM 21, `gfx1013` and `gfx1030` in wave32 and wave64 agree on the same **29 distinct** VS spans with exactly three remaining instruction sites: one `S_SETPRIO 3` and two signed e64 VGPR `V_CVT_F32_I32` with OMOD1. The unsigned `s10` conversion in three of them is recognized but still needs an explicit binding and rounding contract. No instructions were replaced, omitted from strict accounting, or run.

## Entry and reaching definitions

| Stored start | Same 29 spans on all four reference profiles |
| --- | --- |
| +0 / +24 | LLVM fails at the first instruction; no qualified VS path at either start. In particular, neither gives a checked prologue that initializes MODE or `s10`. |
| +36 | Contiguous to the real `S_ENDPGM`; begins with exactly `S_INST_PREFETCH 3`, followed by `S_SETPRIO 3`. |
| +40 | Same fallthrough suffix starting at `S_SETPRIO 3`, before either signed CVT and all exports. No change in the reaching definitions of the audited operands. |

These are stored-window hypotheses, not programmed entry addresses. Failure at +0/+24 rules out those exact starts **under these references**, not preceding state, a different resident image/entry, or a different hardware dialect. The +36/+40 agreement does not establish native wave size. The prefetch makes the streams different for fetch/timing even though it is not a reaching definition for these values.

Scan each contiguous suffix without resynchronization. There are no branches, calls, EXEC writes, scalar memory instructions, writes to ordinary SGPRs, or instruction-mediated writes to the relevant MODE fields (`S_SETREG*`, `S_ROUND_MODE`, `S_DENORM_MODE`, or otherwise). The only explicit STATUS write is the priority update. No in-window STATUS read or timer probe observes it. The only entry VGPR read is `v0` in every span; the only ordinary entry SGPR read is `s10` in the three below. These are facts about instruction-mediated def-use, not about launch state or an asynchronous event outside the checked path.

| Spans | Two signed CVT offsets (from stored span start) | Exported result provenance |
| ---: | --- | --- |
| 9 | +60, +68 | POS0; Z and W are constant one. |
| 16 | +60, +76 | POS0; Z is constant zero, W one. |
| 1 | +60, +76 | Same POS0 definitions, then PARAM0 X/Y from the same computed pair. |
| 3 | +68, +84 | POS0; Z comes from the unsigned `s10` conversion and a literal multiply; W is one. |

**Both signed conversions:** following each input's reaching write gives the two different bits of entry `v0`: `v0 & 2` feeds X and `(v0 << 1) & 2` feeds Y. Each source is exactly `0` or `2` regardless of other entry bits. The I32-to-F32 conversion is exact in every rounding direction on this domain, and if applied the multiply-by-two postmodifier is exact too. The X add of −1 and Y subtraction from +1 are exact and nonzero in both cases. No subnormal, overflow, NaN, or cancellation-to-zero case can make rounding or denorm flushing change those X/Y results. This does **not** remove denorm policy from OMOD: under AMD RDNA 2 ISA §§3.5/6.2.2/6.4/12.8, OMOD is applied iff `MODE.IEEE` bit 9 and F32 output-denorm enable bit 5 are both clear. That one predicate applies to both conversions along this unchanged MODE path. For authored low bits `0,1,2,3`, X/Y are respectively `(-1,1), (-1,-3), (3,1), (3,-3)` when scaled; suppressed gives `(-1,1), (-1,-1), (1,1), (1,-1)`. An all-zero-bit observation cannot distinguish them. This is an exact numerical result bound, not a change to the decoder's MODE requirements or to scheduling/exception semantics.

**Three unsigned conversions:** the e32 read at stored +44 is immediately after SETPRIO in all three and reads the incoming raw `s10` word. Its result reaches only the literal multiply and then POS0.Z, not either signed CVT or X/Y. The exact positive multiplier is `0x37800080`. For any U32 source, the conversion and product are zero or normal finite, so flushing subnormals cannot change Z; the F32 rounding direction can affect the conversion and the multiply. The local code supplies neither a rounding mode nor a bound tighter than U32 for the entry value. An exact conversion does not imply an exact product.

**SETPRIO:** RDNA 2 ISA §§3.4/12.5 specifies `STATUS.USER_PRIO[4:3] ← 3` for this exact immediate, not a MODE write and not an ordinary SGPR definition. It does not set `SPI_PRIO`. USER_PRIO participates in wave arbitration with SPI priority and wave age. No visible in-window read is not evidence of scheduling equivalence; even a bit-exact position comparison is not a test for this instruction's effect.

## Launch ABI constraints and minimum evidence

AMD RDNA 2 ISA §§3.12.1–3.12.2 distinguishes software stage labels from hardware launch roles. It sources the initial PC from stage program registers and the initial round/denorm fields from the applicable `SPI_SHADER_PGM_RSRC1_*`. The published **standalone hardware VS** SGPR table packs enabled inputs: `U` user-data dwords first (`SPI_SHADER_PGM_RSRC2_VS.user_sgpr`), followed by enabled system words. Conditionally on that role, `s10` is user-data dword 10 only if `U >= 11`; otherwise it is system word `10 − U` (zero-based) only if that packed word exists. The table lists at most ten trailing words, so `U=0` cannot initialize `s10` by that VS table; for `1 <= U <= 10`, at least `11 − U` trailing words must be enabled. Merged roles have a different prefix; applying the standalone VS arithmetic merely because of the library slot label is invalid. None of this maps `s10` to a logical root constant, a vertex ID, a descriptor, or an immediate. The [validated library joins](shader-pipeline-library.md#metadata-and-source-digest-joins) identify stage/metadata provenance, not a selected native launch. Neither the opaque stage records nor the compute FSSM register checks establish a graphics register map here.

1. **First, identify the resident program and hardware launch.** In a same-build PSO/draw record, match the resident stage bytes at the programmed PC to the checked body, with actual hardware role, wave size, and any preceding code or fixups. A static library row or the agreement of the two decoder wave settings does not supply this identity.
2. **Then obtain the effective mode.** For the X/Y numerical gate, one effective `IEEE || F32_output_denorm_enable` value suffices for both signed sites if the identified path is unchanged; record its two raw MODE bits [9] and [5] or a verified equivalent initialization and absence of an intervening write. Output-denorm controls OMOD even when no actual denormal can occur. For the three Z paths, also obtain F32 rounding [1:0] before `s10` CVT and MUL (one sample under the same no-write condition). A MODE sample at one signed conversion is transferable to the other only with that execution/path identity. A native pre-raster export/control lane with one set input bit can discriminate scaling vs suppression, but cannot recover both underlying bits or native rounding.
3. **Only the three Z paths require scalar provenance.** Capture the raw wave `s10` at the use and its producer: decoded stage-specific user-data count/enables and relevant programmed user-data slot or hardware-generated system input, or a proven earlier reaching definition if the verified entry is different. A register sample suffices for that wave's numerical check, not a reusable binding. Record active lanes and entry `v0` low bits for any comparison; POS0 and the one PARAM0 export still need an explicit consumer/linkage contract.
4. **Keep SETPRIO separate.** A before/after STATUS sample with incoming USER_PRIO not equal to 3 can discriminate the status write from a no-op. That still does not validate arbitration; strict support needs a faithful priority/scheduler contract with an independently observable scheduling test, not a Metal pixel result.

## Owned combined X/Y/Z oracle

The isolated `owned_vertex_xyz` Metal compute entry checks pre-raster arithmetic, not native VS translation. It takes four authored `v0` words (low bits 0–3, varied upper bits) and one explicit raw `(MODE, s10)` pair shared by all four invocations for a given case. The full matrix crosses all eight IEEE/F32-denorm combinations with all four F32 rounding codes and four scalar substitutions (`0`, `65535`, `2^24+1`, `UINT32_MAX`), for 128 cases. Changing only the scalar word leaves the X/Y goldens untouched; changing only the OMOD policy leaves Z and the intermediate unsigned conversion untouched.

Readback is raw `[X, Y, Z, unsigned CVT]`, not an export or rasterization. RNE uses strict Metal conversion and multiplication. The three directed modes use independent integer-significand rounding at each operation in the MSL probe, not a Metal hardware MODE switch (down and toward zero coincide on this nonnegative domain). The literal raw goldens use separately cross-checked exact binary64 references for each operation. `65535` leaves CVT unchanged but its exact pre-round product `1 − 2^-32` distinguishes RNE Z `0x3f800000` from downward `0x3f7fffff`. `2^24+1` distinguishes RNE CVT `0x4b800000` from upward `0x4b800001`; its RNE two-stage Z `0x43800080` also differs from rounding the direct product once (`0x43800081`).

On Apple M4, **2,048/2,048 raw words** matched independently from runtime MSL source, strict offline metallib bake, and fresh-process strict archive replay (`FailOnBinaryArchiveMiss`). Run `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer sh tools/shader-inventory/smoke-legacy-mul-edges.sh`. The probe does not read native launch state, implement SETPRIO, model scheduling, or admit any shader.
