# Narrow Scarlett command-list submission candidate

Static observations on the image pinned in the [ABI map](xbox-d3d12-abi.md), not live order. RVAs are image-relative. The earliest reachable submission has not been established; below is the smallest positive-count candidate whose list provenance is visible. No title execution or provider changes.

## Single-list wrapper versus batched path

| Call | Measured Win64 operands |
| --- | --- |
| Queue-shaped receiver **#35** (`+0x118`), `02482689` → `0248268f` | Wrapper `02482660` preserves `RCX` from its caller, zero-extends incoming `DL` to select a slot in the list pointer array `075e7300`, passes `EDX=1`, `R8=&array[index]`, `R9=*075e0e88`, and a **dword** zero at caller `[rsp+0x20]`. No consumed status in the wrapper. It passes the address of a pointer, not the list object in `R8`. |
| Same slot, `024821dd` → `024821e3` | `RCX=R15` (selected record's receiver), `EDX=R13D`, `R8=&stack_array`, same `R9` global, stack dword `3`. Entries are copied from work records' `+8` fields (`0248215e`–`02482175`), with a flush boundary at `0x100`. After the call, the batch path invokes associated objects' slot 0 on separate record fields (`024821ee`–`02482209`); those are not calls on the list pointers passed in `R8`. Do not extend a single-list hypothesis to batching or these callbacks. |

Both direct callers of the wrapper found in a rel32 scan (`024821b4`, `02482493`) forward `R15` and stack byte `[rsp+0x37]`. These originate from a selected record (`02481fba`–`02481fe7`, offsets `+0/+8` in a record of stride `0x48`), not a hardwired direct queue or index zero. Index zero resolves to the initial list stored at `02478c0e`; indices 1–4 resolve to the loop-created lists stored at `02478cd9` on successful initialization. The [list audit](scarlett-first-command-list.md) proves successful #73 leads through #132/#131/#9 before storage, not that a particular index is selected first or that the stored lists are empty, never reset, or otherwise ready to execute. The wrapper's failure to validate null or range does not justify omitting validation in an emulator.

`075e0e88` is not an assumed zero or arbitrary test cookie. On the path to the second wrapper call, `0248241e` clears it and device **#80** (`+0x280`) at `02482448` receives `RCX=device`, `EDX=R8D=R9D=0`, caller stack dword `2`, and a sixth argument pointing to the global. The caller sign-checks `EAX`, then consumes the global at `02482458` (and conditionally stores a copy at `02482487`). The other known source is the nonzero qword at `+8` of a type-3 work record, copied to the global at `02482255` before the wrapper; a zero record value takes the #80 path. Another path clears the global after a presentation-shaped call (`024824e7`). These are observations of token-like transport, not a grant, an established lifetime, or proof that zero means “no scheduling”. VIctory `940d32f`, `crates/victory-gpu/src/queue.rs::execute_x`, calls this `{count, lists, token, flags}` and drops token/flags in its own execution model. Its adapter neither verifies Xbox token semantics nor establishes that the SDK's ordinary queue #10 is the path this call takes.

## Separate direct-pool path

The direct pool does not feed the one-list wrapper's `075e7300` array. Its separate #73 initializer (`017f6d34`, IID `5b160d0f-ac1b-4185-8ba8-b3ae42a5a455`) calls list #9 immediately (`017f6d48`); on success the enclosing loop stores the pointer in a pool entry (`017f6c50`). A later consumer takes a pool entry, calls reset-like list #139 (`02474cce`), and places the selected list in a type-zero work record at `0188555`–`018855d`. Those records feed the **batched** #35 at `024821dd`, with stack dword `3`. The initial closed generation is not shown submitted, the later generation is not proven empty, and neither the record callbacks nor device #81's query of a prior tracked token prove completion of this list.

Existing scratch trace `yZhZG2` shows the experiment ended the first empty Metal 4 command buffer at pool #9 (guest return `017f6d4b`), then stopped at the second pool #73 (return `017f6d3b`) before publishing a second list. It reached neither reset nor submission; ending the host buffer is not proof of native Xbox Close semantics.

## Next gate

- **Observed candidate to capture:** queue-shaped #35 at return `0248268f`, count exactly one, fifth dword zero. Capture receiver identity, selected list slot and closed-generation provenance, full `R9`, and whether it came from device #80 or a work record. At a diagnostic stop, log the raw `R8` address; read at most one pointer, only through bounded validation of the title mapping. Stop before submission if the receiver/child state, token, or recorded command effects are not supported. If `024821e3` or another producer comes first, report its shape instead of assuming the wrapper ran.
- **Smallest owned exercise:** one owned queue and closed list, one valid pointer in a guarded array, original counted command and a distinct 64-bit token with a separate stack dword zero. Independently verify argument transport, one execution and completion, retain list dependencies until completion, and reject unknown receiver/list, stale/open generation, unreadable/oversized array, or unsupported token/flags before enqueue. These are test contract choices; an owned marker/readback cannot prove that either pre-close sync operation or token semantics may be elided.
- **Native execution readiness is still open.** Require the actually reached creation/sync/close sequence, provenance of selected queue/list and recorded state, and an evidence-backed token policy before claiming a guest list submitted. A backend-owned marker or an empty fabricated list may verify the backend but is not guest submission. The single-list shape is narrower than the batch shape; it is not a license to bypass the intermediate methods or publish fake completion.
