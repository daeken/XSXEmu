# Xbox Series D3D12 startup ABI map

This is a caller-side map, not a header or a provider contract. **Observed** means statically checked on one AMD64 Scarlett title executable (120,181,760 bytes, SHA-256 `e95020b2fa4a721db3df59fdecf75621730ac559d8835252f6c3b658d5a08993`), not a runtime trace or a claim about every GDK revision. **Projection** names the best-fit operation/type or a possible adapter direction. **Open** items need more evidence before implementation. No title or console DLL was executed.

Offsets are RVAs, not file offsets; preferred image base is `0x140000000`. Slots are zero-based, including the `IUnknown` prefix; vtable entries are eight bytes. Register maps are from the caller immediately before the call. `S20`, `S28`, and `S30` mean hex offsets from the caller's pre-call `RSP` (callee entry offsets are eight bytes higher). An `EAX` sign test establishes HRESULT-like consumption, not the full result contract.

## Imported startup functions

Both functions are imported **by name** from `d3d12_xs.dll`. The IAT in this executable starts at RVA `06793c08` for these three imports: `D3D12ConfigureVirtualMemoryX`, `D3D12SerializeVersionedRootSignature`, `D3D12XboxCreateDevice`, in that order. PE import hints are not export ordinals. Root-signature serialization is out of scope here.

| Import | Observed | Projection and open questions |
| --- | --- | --- |
| `D3D12ConfigureVirtualMemoryX` | Call `01e1cfe0` via thunk `05f3fd60`. `RCX` points to writable-backed stack storage; caller zeros 32 bytes, then writes a dword at `+0x04`. It computes `ceil(reserve_bytes / 16 GiB) + 2` for the locally selected 16/24 GiB reserve (values 3/4); the helper at `04da2350` just returns its input in this image. The caller breaks on negative `EAX`, then uses the selected size for `XMemVirtualAlloc` calls. | One opaque configuration pointer, HRESULT-like result. This arithmetic does not name the field or specify the memory policy. We do not know null handling, complete layout, parameter direction, or what successful configuration must establish. Prior-art stubs returning success are not semantics. |
| `D3D12XboxCreateDevice` | Call `024785b7` via thunk `05f3fd80`: `RCX=0`, `RDX=block`, `R8=&iid`, `R9=&device_pointer`. Caller sign-tests `EAX`; on success it takes the output pointer and makes device calls. At `02478564`–`024785ad` the caller zeros `+0x00..+0x4f` of the parameter storage and overwrites dwords at `+0x00=0x20004`, `+0x08=0x100000`, `+0x20/+0x24=byte-derived values`, `+0x28=1`, `+0x3c=0x20`. | Best-fit roles: optional adapter, opaque creation parameters, IID, out interface. Published field names suggest version/ring size at `+0/+8`, and a flags field at `+0x3c`, but SDK versioning, meanings of bits and the exact callee layout are open. Only an 80-byte caller-initialized span is established here; `+0x50` starts a saved XMM register, so a prior-art 24-dword log is not a basis for reading 96 bytes here. No desktop `D3D12CreateDevice` substitution: desktop takes a scalar feature level in `EDX`, not a pointer in `RDX`. |

## Device and returned-heap calls

| Receiver / slot | Observed callsites and machine shape | Projection, desktop comparison, and limits |
| --- | --- | --- |
| Device **26** (`0xd0`) | `0247870d`, `02478731`, `02478758`: `RCX=stack result storage`, **`RDX=device`**, `R8D=1`, `R9D=1/2/3`. The dispatch loads the vtable **from `RDX`**. These calls do not consume `RAX`. | Likely `GetCustomHeapProperties` with node mask and heap type; desktop slot 26 is that method, but desktop Win64 puts `this` in `RCX` and the return buffer in `RDX`. Neither exact result layout/size nor a requirement to return the storage pointer in `RAX` is established here. Do not apply this ordering to other methods without checking their callers. |
| Device **48** (`0x180`) | `02478813`, `02478853`, `02478893`, `024788d3`: `RCX=device`, `RDX=description storage`, `R8=&queue_iid`, `R9=&out`; sign check. Each call writes a 16-byte span of that storage. Its first dword is `2`, versus `0` at the nearby slot-8 queue call `0247878a`. | Queue creation variant, not desktop slot 48 (`OpenExistingHeapFromAddress`). First dword is consistent with the desktop compute/direct type values. Do not infer a complete `D3D12_COMMAND_QUEUE_DESC` or extension tail: one initialization duplicates a qword across the 16-byte span, and the layout has not been verified at the callee. Exact word meanings, valid combinations and readable length are open. |
| Device **73** (`0x248`) | `02478b71`, `02478c70`: `RCX=device`, `RDX=description storage`, `R8=allocator output of device #9`, `R9=0`, `S20=&console_list_iid`, `S28=&out`. Caller initializes 16 bytes of description storage; leading dwords are `0` and `2` on the two paths. Sign check then immediate dispatch through the returned list. | Command-list creation variant, not desktop slot 73 (`CreateShaderCacheSession`). Leading dword is consistent with command-list type; initial PSO is a plausible role for the null argument, not measured with a non-null value. Description field meanings, full layout and console-list lifetime/interface behavior remain open. |
| Device **133** (`0x428`) | `01e8684c`: `RCX=device`, `RDX=address just passed to XMemMapPhysicalPages`, `R8=stack description`, `R9D=0xffffffff`, `S20=0`, `S28=&resource_iid`, `S30=&out`. The description has a leading dword `1`, a 64-bit span at `+0x10`, and other initialized fields; sign check. | Fits `CreatePlacedResourceX` on already-mapped memory; the description prefix is consistent with a buffer. The null argument could be a clear-value pointer. No corresponding desktop slot 133 in the pinned headers. Do not pass the state sentinel to desktop D3D12, assume a complete desktop resource description, or replace the mapping with a separate committed buffer: the latter would not share the title's mapped bytes. Exact state/flags and GPU visibility/coherence are open. |
| Device **14** (`0x70`) | `01cf32fa`, `01c7453f`, `01f75fb1`: `RCX=device`, `RDX=description storage`, `R8=&heap_iid`, `R9=&out`; sign check and calls on the returned heap. Some sites initialize the 16-byte description from a constant. | Matches the role of desktop `CreateDescriptorHeap`, not proof of layout parity or host heap compatibility. Creation state and CPU handle address requirements matter to this caller (see next row). |
| Descriptor heap **9** (`0x48`) | `01cf3358`, `01c74559`, `01f75fcb`: `RCX=heap`; caller does not set a return-buffer argument and consumes full `RAX`. At `01cf3358`, base is stored and compared for equality with a caller-held value when that value is nonzero; mismatch reaches a break. Other sites use `RAX` in descriptor address arithmetic. | CPU start handle, returned as a 64-bit value on these paths. Desktop Win64 heap slot 9 takes a hidden return buffer in `RDX`. An ABI-correct return alone is not sufficient: an arbitrary host token will not satisfy the observed equality check. Do not infer heap slot 10, allocation policy, descriptor contents, or address ownership from this row. |

Independent increment evidence outside the wrapper: the slot-14 call at `01f75fb1` passes the four dwords `(0, 3128, 0, 1)` copied from `061ecfb0`. The heap slot-9 call at `01f75fcb` supplies the initial address in `RAX`. The device slot-15 call at `01f75fdd` takes `EDX=0` (matching the description's first dword), and the caller repeatedly adds its zero-extended `EAX` return to the address at `01f76010` and `01f7602a`. This supports the increment role of slot 15; it does not reveal a numeric increment. A first dword of zero is consistent with the desktop CBV/SRV/UAV heap category, but neither that mapping nor the complete description layout is established by this call.

See [Title-addressed descriptor heaps](title-descriptor-heaps.md) for the slot-14 wrapper's expected-base provenance, slot-15 stride arithmetic and optional slot-10 return. Those observations do not fix a numeric stride, heap layout, or callback ABI.

## Rechecking the evidence

On a lawfully obtained copy with the matching hash, use `llvm-objdump -p "$exe"` to locate `d3d12_xs.dll` and its IAT; use `llvm-objdump -d --start-address=0x142478560 --stop-address=0x1424785e0 "$exe"` for the creation call (on macOS use `xcrun llvm-objdump`). For other rows inspect before and after each listed RVA plus the image base, starting at an instruction boundary. Follow IAT thunks, and resolve RIP-relative addresses before decoding the referenced GUIDs. For reading data manually, map RVAs through the section table: `file_offset = PointerToRawData + RVA - VirtualAddress` only within the section's raw data. No execution or trace hook is required.

* Desktop comparisons: [`microsoft/DirectX-Headers`, `75edcf75f4c0942dd0d39e75fdc5c42ca6f285fd`, `include/directx/d3d12.h`](https://github.com/microsoft/DirectX-Headers/blob/75edcf75f4c0942dd0d39e75fdc5c42ca6f285fd/include/directx/d3d12.h). Count methods in the C-interface vtable in the `_WIN32` branch, not both platform branches. `ID3D12Device16` has 104 entries in this snapshot. This is a desktop comparator only.
* Local GPL factual references, no implementation copied: Leonida `docs/retail_boot_chain.md` §§1, 3 (reported startup sequence and adapter experiments), `docs/d3d12_xs_surface.md` §§2, 7.1 (export naming and pointers to public parameter names); XCL `91f9a5e9f03156ea82dc55a18f7704862da7a5db` `HANDOFF.md` (other title list IIDs) and `crates/xcl/src/hle/d3d12x/mod.rs` (reference call shapes, not a specification of behavior). The register and buffer-init observations above were independently checked.

## Trusted-offline VM bring-up

`--experimental-static-tls --trusted-offline --rust-providers` binds the direct named `d3d12_xs.dll!D3D12ConfigureVirtualMemoryX` import to a fixed Win64 bridge. There is no desktop alias, dynamic lookup or raw host entry. After restoring host GS, the provider takes a checked 32-byte snapshot from `RCX`. Only a little-endian dword of 3 or 4 at `+0x04` with every other byte zero returns `S_OK`. The provider records that opaque word in the child and logs that it skipped Xbox D3D12 VM policy, VA reservation/backing, GPU mappings, and CPU/GPU visibility. It does not write to the caller's block or change XMem state. Null/unreadable input returns `E_INVALIDARG`; other shapes return `E_NOTIMPL` without changing the record. These status choices describe the shim, not real Xbox behavior.

The owned `static_tls_lane` fixture exercises the IAT bridge with the observed register and input shape, and checks failure statuses and profile/provider isolation. A separate guard-page test checks the snapshot ends at byte 32 and that rejected calls preserve the record. Neither test needs title assets.

## Owned ABI probe and implementation boundary

`cargo test --offline --target x86_64-apple-darwin --test xbox_d3d12_abi` runs the original slot-26 probe on x86-64 (Rosetta on Apple Silicon); other x86-64 hosts can run the same test with their native target. The assembly caller supplies an owned vtable, shadow space, and the observed register order; a typed `extern "win64"` callee records distinct values into separate writable storage. The output is a synthetic ledger, not an Xbox heap-properties type. The test intentionally ignores `RAX` and registers no export or provider.

The [macOS CPU alias proof](xmem-cpu-alias.md) exercises shared backing and view lifetime with real host mappings. It does not verify `XMemMapPhysicalPages` or the GPU placement and visibility needs of slot 133.

Do not dispatch by desktop slot number or silently report success for unknown VM/resource/heap semantics. Before exposing device creation, establish hardware-independent ownership and error behavior for the observed interfaces, determine the required inputs at the opaque boundaries, and verify that descriptor addresses and mapped memory remain coherent with the guest view.
