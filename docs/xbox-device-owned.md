# Owned Xbox D3D12 device lifetime foundation

The [static startup trace](xbox-d3d12-abi.md) observes `RCX=0`, `RDX=&caller_block`, `R8=&IID`, and `R9=&out` at `D3D12XboxCreateDevice`. It establishes an 80-byte initialized prefix and the requested UUID, not a complete Xbox parameter type, adapter policy, or device-creation semantics. The matching desktop UUID does not justify a desktop device vtable.

`xbox_device::OwnedDevices` is a bounded identity/refcount ledger, not a provider. Creation requires the observed request UUID, no adapter, an exact match against the caller-selected opaque fixture profile, available capacity, and an available backend. It retains the checked prefix and gives the object one reference. This fixture profile is synthetic, not an accepted Scarlett creation block. The model's `QueryInterface` recognizes `IUnknown` and that same UUID with one canonical identity. Unsupported queries do not acquire references. Overflow is an error; final release removes the record and IDs are not reused. ID checks do not make a released native pointer safe to dereference.

`cargo test --offline --target x86_64-apple-darwin --test xbox_device_owned` uses original Win64 assembly and a private vtable implementing only IUnknown. A subprocess confirms that calling an unsupported slot terminates explicitly, with no dispatch through a desktop table. The fixture is opt-in, checks the observed register order, snapshots exactly 80 parameter bytes and 16 IID bytes using Mach reads, and uses checked pointer-sized Mach writes to clear and publish the out pointer. A read-only mapping and adjacent guard page check write rejection, exact span acceptance, and rejection of a one-byte overread. The kernel checks mappings, not Windows guest ownership; these checks are not a sandbox. Fixture return codes describe the owned contract only.

The fixture requires a real `MTLDevice` and a `newCommandQueue` return. It tests a denied backend factory separately, and verifies that the retained backend's release path runs exactly once at final COM `Release`, not at intermediate decrements. It does not assert that Metal itself deallocates its system device. The ledger tests separately cover reference overflow, capacity, stale IDs, and cross-ledger rejection.

The second test creates two owned devices through Win64. Private fixture-only Win64 calls return a queue key tied to each live device and submit one fixed 64-byte copy. Both directions of queue-key swapping fail before any submission or output change. The successful copy uses the owning device's already retained Metal queue and distinct shared buffers; it does not look up another device or queue. The [command model](d3d12-command-state.md) validates before Metal commit and records acceptance only after that commit. The allocator remains pinned until the same command buffer reports `Completed` and all 64 copied bytes match. Only then does the fixture retire the model token and reset the allocator. Metal errors or a five-second polling deadline fail without claiming completion. Repeat submission and submission through a released owner are rejected.

No title-lane registration, title execution, Xbox VM setup, guest command queue/list, descriptor, or success for an unimplemented Xbox operation is added. The private fixture calls are not retail exports or vtable slots; the retained-backend borrow grants neither a GPU address mapping nor a guest method. A production guest facade would require audited checked input/output, guest-safe vtable entries (including a terminal unsupported path), actual object behavior and live evidence for the enabled scope.
